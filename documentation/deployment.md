# Deployment Documentation

## 1. Project Scope

This document describes the implementation of the high-availability and auto-scaling web application infrastructure developed during the AWS practical exercises.

The infrastructure evolved progressively by reusing resources created during previous exercises and adding new AWS components and configurations.

The main components documented in this project are:

- Amazon EC2
- Application Load Balancer (ALB)
- Target Group
- Security Groups
- Auto Scaling Group (ASG)
- Launch Template
- Amazon CloudWatch

---

## 2. Initial EC2 Infrastructure

Two Amazon EC2 instances were launched to host the web application.

The instances were configured to provide access to the application through HTTP.

The instances were subsequently used as targets behind the Application Load Balancer.

## 3. Target Group

A Target Group was created to group the two EC2 instances.

The instances were registered as targets and monitored using health checks.

The Target Group allowed the Application Load Balancer to determine which instances were healthy and available to receive traffic.

---

## 4. Application Load Balancer

An Application Load Balancer was configured as the public entry point to the application.

The Load Balancer was configured to receive HTTP traffic and forward requests to the Target Group.

The application was accessed through the DNS name assigned to the Load Balancer.

This provides a single endpoint for users instead of exposing the individual EC2 instances as the primary application endpoint.

---

## 5. Availability Zone Configuration

The Load Balancer was configured across the available Availability Zones selected during the deployment.

The purpose was to distribute the infrastructure across multiple Availability Zones and improve application availability.

---

## 6. Security Group Configuration

The Security Groups were configured to control communication between the Application Load Balancer and the EC2 instances.

The EC2 instances were configured to accept HTTP traffic from the Security Group associated with the Application Load Balancer.

This prevents direct HTTP access to the instances through their public IP addresses and makes the Load Balancer the controlled entry point for the application.

---

## 7. Failure Detection Test

To validate the Load Balancer health-check mechanism, one of the EC2 instances was stopped.

The Target Group detected that the instance was no longer healthy.

The Load Balancer then stopped sending application traffic to the unavailable instance.

The EC2 instance was subsequently started again.

This test simulated an instance failure and demonstrated the health-check behavior of the Load Balancer and Target Group.

---

## 8. Sticky Sessions

Sticky Sessions were configured on the Target Group.

The configuration enabled session persistence using a cookie generated by the Load Balancer.

The behavior was validated by accessing the application through the Load Balancer and refreshing the page.

After enabling persistence, the client continued to be directed to the same backend instance.

---

## 9. Auto Scaling Launch Template

A Launch Template was created for the Auto Scaling configuration.

The template defined the configuration used when new EC2 instances were launched by the Auto Scaling Group.

The Amazon Machine Image (AMI), instance type and storage configuration were selected as part of the template.

---

## 10. Auto Scaling Group

An Auto Scaling Group was created using the Launch Template.

The Auto Scaling Group was associated with the Load Balancer infrastructure and configured to maintain the desired number of EC2 instances.

A minimum capacity of two instances was configured for the practical exercise.

---

## 11. Automatic Instance Replacement

An EC2 instance managed by the Auto Scaling Group was removed to simulate an infrastructure failure.

The Auto Scaling Group detected that the number of running instances was below the configured capacity.

A new EC2 instance was automatically launched using the Launch Template.

The new instance was then incorporated into the infrastructure managed by the Auto Scaling Group.

---

## 12. Dynamic Scaling

A dynamic scaling policy was configured for the Auto Scaling Group.

The policy used CPU utilization as the metric for scaling decisions.

The objective was to increase the number of EC2 instances when the workload increased.

---

## 13. Load Generation

CPU load was generated on an EC2 instance using the Linux stress utility.

  The following commands were used: sudo amazon-linux-extras install epel -y
  sudo yum install stress -y
  stress -C 4
The resulting CPU utilization was monitored through Amazon CloudWatch.

The test was used to validate the behavior of the dynamic scaling configuration.
